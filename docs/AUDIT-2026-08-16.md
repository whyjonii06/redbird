# Audit Redbird — 16 août 2026

Analyse complète de parité fonctionnelle vs PrestaShop v9, avec un œil sur les
plateformes headless (Shopify, commercetools, Shopware) là où Redbird sort du
cadre "clone PrestaShop" pour devenir composable.

## Structure du monorepo

**Apps (6)** : `backoffice`, `marketplace` (site SaaS landing/pricing, distinct
de la marketplace de plugins qui vit dans le backoffice), `storefront` (Vite,
SSR complet), `storefront-classic` / `storefront-editorial` / `storefront-b2b`
(Next.js 15, découplés du core — client tRPC pur).

**Packages (8)** : `core`, `api`, `api-types` (surface de types tRPC pure,
zéro dépendance runtime — la brique du "composable"), `cli` (forge),
`create-shop`, `create-storefront`, `plugin-sdk`, `trpc`.

**Plugins (11)** : stripe, paypal, shipping-flat, shipping-zones,
shipping-mondial-relay, vat-eu, tax-rules, reviews, email-resend, email-smtp,
email-local, analytics.

**Autre** : `tests-integration`, `services/license-server` (Hono + SQLite +
Stripe, hors du workspace pnpm — infra de licensing SaaS séparée).

**Échelle** : 44 migrations Drizzle séquentielles (`0000` → `0044`).

## Ce qui est implémenté

### Le cœur métier (packages/core)
Catalogue (variantes, images, recherche, i18n BCP47, catégories, marques,
fournisseurs, produits virtuels), panier (multi-devise avec conversion réelle
via taux ECB/Frankfurter), commandes (state machine complète), stock
(réservation/warehouses), promos, avis, retours, staff RBAC, CMS, groupes
clients avec tarifs par palier, points de fidélité (consommés au checkout),
programmes marketing (opt-in newsletter avec segmentation), quote requests B2B,
POS (sessions de caisse, ventes réelles), abandoned-cart cron automatique,
multi-tenant (scoping appliqué au niveau requête, pas juste une colonne).

### Fiscalité & légal — anciennement le plus gros trou, maintenant un point fort
TVA calculée réellement au checkout (`taxes.default()`, validation VIES avec
repli si VIES est indisponible), factures PDF générées à la volée, **Factur-X**
(PDF/A-3 hybride avec XML EN16931 embarqué — la norme française de
facturation électronique), export FEC. GDPR réel : export de données client et
anonymisation de compte, exposés jusque dans l'UI storefront (confirmation
tapée avant suppression).

### Backoffice (apps/backoffice)
Dashboard, produits (upload d'images réel — plus juste des URLs), commandes,
retours, clients (carnet d'adresses multi-adresses), groupes/prix B2B,
**devis B2B** (cycle complet demande → contre-offre staff → accepté/refusé),
**Caisse (POS)**, **Marketplace** (plugins + thèmes, install/désinstall à
chaud sans redémarrage serveur), staff RBAC, reports, CMS, réglages, setup
wizard.

### Storefront principal (apps/storefront)
SSR réel — pas juste un shell client-side avec meta injectées après coup.
`entry-server.tsx`/`entry-client.tsx`/`server.js` : QueryClient et client tRPC
isolés par requête, prefetch product/category, meta/JSON-LD servis dans le
HTML initial, hydratation sans mismatch (auth/panier/devise/locale déférés à
un effect post-mount). PWA (manifest, service worker, prompt d'installation).
Compte client complet (adresses, RGPD, retours, factures, abonnements).

### Storefronts headless (classic / editorial / b2b)
Découplés du core — consomment uniquement `@redbirdshop/api-types` via un
client tRPC vanilla. Confirmé : aucun import direct de `@redbirdshop/core`
dans les trois thèmes. C'est la vraie porte d'entrée "composable" : n'importe
quel front (Next.js, Nuxt, mobile natif...) peut brancher `api-types` sans
jamais toucher au moteur.

### B2B — différenciateur, pas dans PrestaShop cœur
Groupes clients avec conditions de paiement Net-30, bons de commande
(`poNumber`/`dueDate` sur les commandes), devis négociés, tarifs par palier de
quantité.

### Multi-boutique — feature phare annoncée pour PrestaShop v9, ici réelle
`tenants` + `tenant_id` sur customers/products/categories/carts/orders, avec
`tenantFilter()` appliqué au niveau service (catalog, cart, order, customer) —
pas juste une colonne dormante.

### Écosystème plugins
Marketplace en place avec install/désinstall/reconfiguration à chaud (aucun
redémarrage serveur nécessaire — vérifié en live). 11 plugins first-party
couvrant paiement, livraison, taxes, email, avis, analytics.

### CI/CD
`.github/workflows/ci.yml` — lint (Biome), typecheck + build + test (291 specs
sur PGlite) à chaque PR.

### Scaffolding
`forge create` reste minimal (4 fichiers statiques), mais deux outils séparés
et bien plus complets existent : `create-redbird-shop` (API + storefront +
PGlite embarquée, zéro config) et `create-redbird-storefront` (Vite + React +
tRPC autonome).

Aucun. Tous les points bloquants de l'audit de juin (TVA à 0, upload d'images,
factures PDF, RGPD, reset mot de passe, CI/CD) sont maintenant réels et câblés
de bout en bout.

### **Total estimé : ~74% de parité fonctionnelle avec PrestaShop v9**

*(Pondération identique à l'audit de juin, pour rester comparable — ~23% → ~74%
sur les deux derniers mois.)*

Ce score sous-compte volontairement trois capacités que PrestaShop v9 n'a pas
nativement, et qui ne rentrent dans aucune ligne du tableau ci-dessus :

- **B2B natif** (devis, Net-30, bons de commande, tarifs par palier)
- **POS natif** (caisse, sessions, ventes en magasin)
- **Architecture composable/headless** (`api-types` + 3 thèmes découplés,
  install de plugins à chaud) — PrestaShop reste un monolithe à modules PHP,
  redémarrage requis.

## Lecture

Le chantier de juin identifiait 6 points bloquants pour toute mise en
production réelle (TVA, upload images, factures, RGPD, reset password,
CI/CD) — les 6 sont faits, et pour la fiscalité/facturation, Redbird va même
au-delà de ce que fait PrestaShop nativement (Factur-X, export FEC).

Les deux chantiers qui restent réellement structurants :

1. **Bundles produits** — le seul trou fonctionnel "cœur catalogue" restant.
2. **Outil de migration PrestaShop par IA** — identifié comme USP unique dès
   juin, toujours pas commencé. C'est le chantier qui transformerait Redbird
   d'un "moteur complet mais inconnu" en "remplacement crédible" pour les
   ~300 000 boutiques PrestaShop existantes.

Le reste (transporteurs, doc publique, npm publish) est de l'écosystème —
important pour l'adoption, mais aucun n'est bloquant pour vendre en
production dès aujourd'hui.
